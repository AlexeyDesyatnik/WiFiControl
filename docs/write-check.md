# Проверка записи настроек IPv4 на Windows 11

Этап 1 [плана](roadmap.md): до основного кода проверить на Windows 11, что перенесённые из NetSwitch команды ([ADR 0003](adr/0003-settings-written-as-in-netswitch.md)) работают на Wi-Fi-адаптере без соединения — а у нас это основной сценарий переключения ([ADR 0004](adr/0004-ipv4-before-connect.md)). На Windows 10 этот путь проверен в NetSwitch ([ADR 0003 NetSwitch](https://github.com/AlexeyDesyatnik/NetSwitch/blob/main/docs/adr/0003-dhcp-without-connection-through-msft-netipinterface.md)).

Проверяет сценарий [`tools/write-check/write-check.ps1`](../tools/write-check/write-check.ps1). Он **меняет настройки IPv4 Wi-Fi-адаптера** и в конце возвращает DHCP. Второй адаптер не нужен: команды локальные, интернет на время проверки не требуется.

## Что проверяется

Два случая возврата к DHCP, оба на отключённом Wi-Fi-адаптере:

- **А. Статический адрес был действующим** — адаптер работал в сети со статическим адресом, его отключили и возвращают DHCP перед подключением к другой сети. Основной сценарий переключения.
- **Б. Статический адрес записан, но не применялся** — записали без соединения, подключения не было (откат, неудачное переключение). На Windows 10 обычный netsh здесь отказывает с «DHCP is already enabled», и нужен запасной путь: `netsh delete address … gateway=all`, затем `MSFT_NetIPInterface` в постоянном хранилище. В сценарии запасной путь вызывается через `Set-NetIPInterface -PolicyStore PersistentStore` — это тот же класс.

Заодно сценарий смотрит, не подключается ли Windows сама к другой сети, пока адаптер отключён между шагами переключения.

В первом прогоне (2026-10-26) после подключения со статическим адресом в действующих настройках не оказалось шлюза по умолчанию: адрес действовал, шлюз отвечал на ping, интернета не было, хотя в постоянных настройках шлюз записан. Поэтому на шаге 3 сценарий ждёт шлюз и, если он не появится, пробует два способа его вернуть (шаги 3а и 3б).

Повторные прогоны в тот же день подтвердили это три раза из трёх: маршрут по умолчанию есть, пока адаптер отключён, и пропадает при первом подключении, когда Windows выключает DHCP; через ~16 с перезапускается защита соединения (события 11004, 11010, 11005 журнала WLAN-AutoConfig), ещё через ~16 с — 8003 «disconnected by the driver». Повторное подключение с теми же настройками работает. Шаги 3а и 3б к этому моменту опаздывают, поэтому причину и обход выясняют варианты ниже.

## Подготовка

- [x] Ноутбук с Windows 11, учётная запись администратора.
- [x] Wi-Fi-адаптер подключён к сети `MichLycee` по DHCP. Если на адаптере сейчас ручные настройки — переписать их: сценарий в конце вернёт DHCP.
- [x] Выключить VPN (AmneziaVPN): он перехватывает маршрут в интернет и реагирует на отключение Wi-Fi.
- [x] Выключить точку доступа на телефоне и уйти от других сетей с автоподключением (`HONOR 400`, `ESPD_604`, `WIFINETWORK_4`): иначе Windows подключится к ним сама, пока адаптер отключён. У `MichLycee` автоподключение выключено — это и нужно.
- [x] Выбрать свободный адрес в `MichLycee`. По умолчанию 192.168.1.200/24, шлюз и DNS 192.168.1.1; сценарий сам проверит, что адрес не отвечает на ping. Другой адрес — параметром `-Address`.
- [x] Знать, как вернуть DHCP руками, если что-то пойдёт не так: «Параметры → Сеть и Интернет → Wi-Fi → свойства сети → Назначение IP → Изменить → Автоматически (DHCP)», и то же для DNS. Или запустить сценарий с `-Restore`.

## Запуск

PowerShell **от имени администратора**, в папке репозитория:

```powershell
cd tools\write-check
powershell -ExecutionPolicy Bypass -File .\write-check.ps1
```

`-ExecutionPolicy Bypass` действует только на этот запуск: сценарий не подписан. Если имя адаптера, сеть или адрес другие:

```powershell
powershell -ExecutionPolicy Bypass -File .\write-check.ps1 -Adapter 'Wi-Fi' -Network 'MichLycee' -Address 192.168.1.201
```

`-GatewayTimeout 30` — ждать шлюз на шаге 3 дольше 20 с.

### Варианты для подключения со статическим адресом

Параметр `-Variant` выбирает короткий прогон (около двух минут) вместо полного. Каждый вариант после проверки сам возвращает DHCP и подключается к сети, где был DHCP. `-WatchSeconds` — сколько следить за соединением, по умолчанию 45 с: в наблюдении пишется каждая смена состояния адаптера и маршрута по умолчанию.

| Вариант | Что делает | Что выясняет |
|---|---|---|
| `FastRoute` | Статика на отключённом адаптере, подключение; если маршрута нет 3 с — сразу, без вопроса, добавляет его в действующие настройки | Спасает ли быстрое восстановление маршрута, или Windows всё равно рвёт соединение |
| `AfterConnect` | Подключение с DHCP, затем статика на подключённом адаптере, как в NetSwitch | Работает ли запись после подключения — запасной порядок переключения, противоречащий ADR 0004 |
| `OtherNetwork` | DHCP в одной сети, статика на отключённом адаптере, подключение к другой; без исправлений | Сбой бывает всегда или только когда шлюз прежней аренды совпадает со статическим |

```powershell
powershell -ExecutionPolicy Bypass -File .\write-check.ps1 -Variant FastRoute
powershell -ExecutionPolicy Bypass -File .\write-check.ps1 -Variant AfterConnect
powershell -ExecutionPolicy Bypass -File .\write-check.ps1 -Variant OtherNetwork -DhcpNetwork 'MichLycee' -Network 'HONOR 400' -Address 10.19.210.200 -Gateway 10.19.210.238 -Dns 10.19.210.238
```

Для `OtherNetwork` точка доступа телефона должна быть включена, а адаптер — подключён к `MichLycee`. Адрес 10.19.210.200 сценарий проверить заранее не может (он в другой сети) — если телефон раздаёт другую подсеть, поменять адрес и шлюз под неё.

Перед каждым шагом сценарий объясняет, что сделает, и ждёт Enter; `q` — прервать. После каждого шага он снимает состояние адаптера: состояние и SSID, DHCP в действующих и постоянных настройках, адреса и шлюзы в обоих хранилищах, DNS, значения в разделе реестра `Tcpip\Parameters\Interfaces\{GUID}` (`EnableDHCP`, `DisableDhcpOnConnect` и другие), вывод `netsh interface ipv4 show config`. Проверки помечаются `[ДА ]` и `[НЕТ]`.

## Шаги

| Шаг | Что делает | Ожидается |
|---|---|---|
| 0 | Исходный снимок, предварительные проверки | Подключён к `MichLycee` по DHCP, адрес свободен |
| 1 | Отключить от сети, 15 с наблюдения | Windows сама не подключается |
| 2 | Статический адрес и DNS через netsh, без соединения | Адрес записан как ручной: `DisableDhcpOnConnect = 1` или ручной адрес в постоянном хранилище |
| 3 | Подключиться к `MichLycee`, до 20 с ждать шлюз по умолчанию в действующих настройках | Действует статический адрес, шлюз появился, интернет есть |
| 3а | Только если шлюза нет: повторно записать те же настройки IPv4 на подключённом адаптере | Шлюз появился, интернет есть |
| 3б | Только если шлюза всё ещё нет: добавить маршрут по умолчанию в действующие настройки (`netsh … add route … store=active`) | Шлюз появился, интернет есть |
| 4 | Отключить от сети | — |
| 5 | **Случай А.** Вернуть DHCP обычным netsh; если адрес остался ручным — шаг 5б, запасной путь | Адрес больше не ручной |
| 6 | Подключиться | Адрес по DHCP, время от подключения до адреса |
| 7 | Отключить от сети | — |
| 8 | Статический адрес без соединения | Адрес записан как ручной |
| 9 | **Случай Б.** Вернуть DHCP обычным netsh, не подключаясь; если не вышло — шаг 9б, запасной путь | Обычный netsh, по опыту Windows 10, откажет; запасной путь вернёт DHCP |
| 10 | Подключиться | Адрес по DHCP, не 169.254.x.x; итоговый снимок |

Займёт минут десять–пятнадцать.

## Если что-то пошло не так

- **Windows сама подключилась к другой сети** на шагах 1, 4 или 7 — сценарий остановится. Выключить автоподключение той сети или её точку доступа и запустить заново.
- **Wi-Fi остался без адреса или с 169.254.x.x** после шага 6 или 10 — это и есть найденная проблема, отчёт сохранён. Вернуть DHCP:

  ```powershell
  powershell -ExecutionPolicy Bypass -File .\write-check.ps1 -Restore
  ```

  Если не помогло — руками через «Параметры», см. «Подготовку».
- **Прервали на середине** — тоже `-Restore`.

## Итоги (2026-10-26, Windows 11 26H2)

Ноутбук ALEXD-RIKOR, сборка 26300.9711, Intel Wireless-AC 9560, сеть `MichLycee` (шлюз 192.168.1.1). Четыре полных прогона (один прерван на шаге 3а) и по одному прогону каждого варианта.

| Что | Результат |
|---|---|
| Статика на отключённом адаптере | Записывается как ручная: `DisableDhcpOnConnect = 1`, маршрут по умолчанию в действующих настройках есть |
| Первое подключение со статикой, шлюз тот же, что у прежней аренды DHCP | Адрес действует через ~3 с, но **маршрута по умолчанию нет** — 4 прогона из 4. Интернета нет; через ~32 с Windows перезапускает драйвер (System 4003) и адаптер отключается. Повторное подключение с теми же настройками работает |
| Шаги 3а и 3б полного прогона | Запаздывали: к ним соединение уже было разорвано или переподключено вручную — ничего не показали |
| `FastRoute` | Маршрут добавлен через 3 с после адреса — интернет сразу, соединение держится 45 с |
| `AfterConnect` | Статика на подключённом адаптере действует через 3,5 с, маршрут на месте, соединение держится 45 с |
| `OtherNetwork` (`MichLycee` → `HONOR 400`, другой шлюз) | Маршрут на месте, интернет сразу. Через 27 с — тот же перезапуск драйвера (4003), но он бывает на этой точке доступа и при DHCP |
| Возврат к DHCP, статика была действующей | Обычный netsh работает |
| Возврат к DHCP, статика только записана | Обычный netsh — «DHCP is already enabled» (код 1); запасной путь работает |
| Windows сама подключается, пока адаптер отключён | Нет, но у всех сетей было выключено автоподключение |

Выводы — в Consequences [ADR 0003](adr/0003-settings-written-as-in-netswitch.md) и [ADR 0004](adr/0004-ipv4-before-connect.md). Не проверено: переход в другую сеть со статикой — на другой точке доступа, без перезапусков драйвера; запуск netsh из exe и реакция антивируса.
