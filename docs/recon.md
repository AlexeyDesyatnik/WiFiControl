# Задание на разведочную сборку

Разведочная сборка — отдельная небольшая программа на целевом стеке ([ADR 0001](adr/0001-csharp-net10-wpf.md)), которая **только читает** состояние компьютера и записывает события Wi-Fi. Она ничего не меняет: ни настроек адаптеров, ни прокси, ни профилей сетей Windows. Цель — до основного кода узнать, как ведут себя Windows 10 и Windows 11 24H2+ там, где документации мало или она не про наш случай.

## Где прогонять

Пошагово, со сборкой, задачей Планировщика и тем, что смотреть в каждом сценарии, — [чек-лист прогонов](recon-checklist.md).

- Ноутбук с Windows 10.
- Машина с Windows 11 24H2 или новее.

На каждой — три запуска: вручную с подтверждением UAC; из задачи Планировщика «при входе, с наивысшими правами» (задачу на время разведки создаём руками); вручную при выключенном доступе к местоположению (только Windows 11).

## Что читает

1. **Система**: версия и номер сборки Windows; запущена ли программа с правами администратора и от чьего имени; запущена ли из Планировщика.
2. **Wi-Fi-адаптеры** (`WlanEnumInterfaces`): GUID, описание, состояние; сопоставление с адаптером из «Сетевых подключений» (по GUID, как в NetSwitch).
3. **Текущее подключение** (`WlanQueryInterface`, `current_connection`): SSID, BSSID, имя профиля сети Windows, тип защиты, уровень сигнала, частота. При отказе — код ошибки.
4. **Видимые сети** (`WlanScan`, затем `WlanGetAvailableNetworkList` и `WlanGetNetworkBssList`): SSID, сигнал, защита, BSSID и частоты, есть ли профиль сети Windows. При отказе — код ошибки.
5. **Профили сетей Windows** (`WlanGetProfileList`, `WlanGetProfile` без открытого пароля): имя, режим автоподключения, есть ли в XML элемент о случайном MAC-адресе.
6. **Случайный MAC-адрес**: текущий MAC Wi-Fi-адаптера против постоянного; откуда надёжнее брать признак — из XML профиля сети Windows, из реестра или сравнением адресов.
7. **Настройки IPv4 Wi-Fi-адаптера**: настроенные и действующие, кодом из NetSwitch.
8. **Проводные адаптеры**: состояние, шлюзы, метрики интерфейсов; через какой адаптер Windows отправит трафик в интернет (`GetBestRoute2` или таблица маршрутов).
9. **Прокси**: системный и WinHTTP, кодом из NetSwitch.
10. **Доступ к местоположению**: что записано в разделе `CapabilityAccessManager\ConsentStore\location` (для пользователя и компьютера) — чтобы сравнить с тем, что фактически отвечает WLAN API.

## Что записывает

Пока программа открыта, она пишет в окно и в отчёт все события с точным временем:

- уведомления WLAN (`WlanRegisterNotification`, источники ACM и MSM): начало и конец подключения, отключение, завершение сканирования, смена сигнала — с SSID из уведомления;
- смену адресов (`NetworkChange.NetworkAddressChanged`) с действующими адресами Wi-Fi-адаптера в этот момент;
- сон и выход из сна (`SystemEvents.PowerModeChanged`).

## Сценарии прогона

1. Запуск и чтение — пункты 1–10.
2. Переключение на другую сеть через системное меню Windows.
3. Выход из зоны сети и возвращение (или выключение точки доступа).
4. Сон на несколько минут и выход из сна.
5. Подключение кабеля к сети со шлюзом и отключение.
6. На Windows 11: выключить доступ к местоположению, перезапустить программу, повторить пункты 3–4 чтения; включить обратно — приходит ли запрос Windows при первом обращении.

## Отчёт

По кнопке «Сохранить отчёт» — текстовый файл в папку `Отчёты` рядом с exe, имя `ИМЯКОМПЬЮТЕРА_ГГГГ-ММ-ДД_ЧЧ-ММ.txt`; отчёты накапливаются и не затирают друг друга. В отчёт входят прочитанное, все события и коды ошибок.

## На какие вопросы должна ответить разведка

| Вопрос | Windows 10 | Windows 11 24H2+ |
|---|---|---|
| Работает ли WLAN API из процесса с правами администратора при включённом доступе к местоположению? | Да, всё читается без ошибок. Раздел `ConsentStore\location` есть, везде Allow, но без времени изменения и без записей о классических приложениях. | Да: текущее подключение, сканирование (конец через 2–5 с), видимые сети, профили сетей Windows, уведомления. |
| Какие вызовы и с какой ошибкой отказывают при выключенном доступе? | — | Код 5 (`UnauthorizedAccessException`): `WlanQueryInterface` (`current_connection`), `WlanScan`, `WlanGetAvailableNetworkList` и **`WlanRegisterNotification`** — уведомлений WLAN нет вовсе. Работают: `WlanEnumInterfaces` (состояние Connected видно), `WlanGetProfileList`/`WlanGetProfile`, настройки IPv4, маршруты, `NetworkAddressChanged`. Пока доступ запрещён, время последнего обращения в реестре не обновляется. При включённом доступе запроса Windows при первом обращении **нет**: у копии программы под новым именем обращение записано, а `GlobalPromptShown` не появился. Когда Windows поставила этот флаг первой копии, неизвестно; на решения это не влияет — окно «нет доступа» не может рассчитывать на запрос Windows. |
| Одинаково ли ведёт себя запуск из Планировщика и ручной с UAC? | Не проверяем (см. ниже). | Да: окно при входе без UAC, признак «Из Планировщика» определён верно (родитель — процесс службы Schedule), WLAN API работает так же, как при ручном запуске. |
| Какие уведомления приходят при переключении через системное меню, при автоподключении после сна, при выходе из зоны? | Сон (S3): подключение не переустанавливается — после выхода из сна только MSM `roaming_start` → `authenticating` → `roaming_end` к тому же BSSID, без `connection_start`/`connection_complete`. «Питание: Resume» приходит **после** того, как сеть уже поднялась. Встречается неизвестное MSM-уведомление 59 (рядом с `signal_quality_change`). Переключение и выход из зоны не проверяем. | Переключение: ACM `profile_unblocked` (несколько), `disconnecting`; MSM `connected`, `roaming_start`, `disconnected` (причина «operation cancelled»); ACM `disconnected`, `connection_start`; MSM `associating` (BSSID нулевой), `associated`, `authenticating`, `connected`; ACM `connection_complete`. SSID, профиль сети Windows и BSSID разбираются верно. Пропажа сети: через ~1 с после выключения точки доступа MSM `disconnected` (причина «driver disconnected») и ACM `disconnected`; пока сети нет, при видимых знакомых сетях приходят ACM `network_available`; подключение обратно — той же цепочкой до `connection_complete` (автоподключение у всех сетей было выключено, подключались вручную). Сон с Modern Standby (S0, 6 минут): соединение не рвётся вовсе — ни `disconnected`, ни смены адресов, ни событий питания; после пробуждения только два ACM `screen_power_change`. **Ограниченное подключение:** если через ~16 с после подключения Windows считает подключение ограниченным, она перезапускает защиту (события 11004, 11010, 11005 журнала WLAN-AutoConfig), а ещё через ~16 с — драйвер (System 4003 «limited connectivity, attempting automatic recovery»): MSM `disconnected` «driver disconnected», `interface_removal`/`interface_arrival`, `radio_state_change`. На точке доступа телефона это случается и при DHCP; «перезапуск драйвера при пропаже сети» в первом прогоне был этим. **Открыт:** долгий сон и смена сети во время сна. |
| Сколько секунд проходит от завершения подключения до адреса по DHCP? | После сна ~2 с от «Смены адресов» с Down до Up, адрес прежний. | 0,1–1,3 с от `connection_complete` (в проверке записи — 0,8–1,1 с после подключения), но адрес каждый раз прежний — аренда переиспользована. **Открыт:** получение нового адреса. «Смена адресов» приходит 2–5 раз на один переход, в том числе при подключении и отключении кабеля; в событиях с Down адреса ещё старые. |
| Откуда надёжно брать признак случайного MAC-адреса? | Не проверяем. Известно: элемент `MacRandomization` есть в XML профиля и при выключенной функции; `RandomMacState` в реестре нет; текущий адрес совпадает с постоянным. | Не проверяли: в плане первой версии признак не используется. Известно то же, что для Windows 10. |
| Как определить, что интернет идёт через Ethernet? | Не проверяем. Известно: в таблице маршрутов есть `0.0.0.0/0` на **отключённом** проводном адаптере с метрикой 6, а `GetBestRoute2` верно выбирает Wi-Fi. | Только через `GetBestRoute2`. Маршрут по умолчанию есть и на отключённом проводном адаптере (метрика 1 + 5 = 6 против 35 у Wi-Fi), и `GetBestRoute2` его верно не выбирает. С линком USB-адаптер на 100 Мбит/с получил автоматическую метрику 35, его маршрут 1 + 35 = 36 проиграл Wi-Fi (0 + 35) — интернет остался на Wi-Fi. Автоматическая метрика Wi-Fi за день менялась от 25 до 55, так что исход сравнения заранее не предсказать. |
| Хватает ли ManagedNativeWifi или нужен собственный P/Invoke? | Для чтения хватает. Отказы приходят как `UnauthorizedAccessException` с `MethodName` и кодом — их легко сопоставить с вызовом. Уведомления — собственный P/Invoke, как в разведочной сборке. Подключение разведка не проверяет. | То же. |
| Как выглядит Fluent-тема WPF? | Не проверяем. | Прилично. В ленте событий строки слишком высокие и обрезаются справа (нужна горизонтальная прокрутка). Первый запуск самодостаточной сборки — ~15 с до окна, следующие — меньше секунды. |

Ответы заносятся в эту таблицу; то, что меняет решения, — в новые ADR или в Consequences существующих.

**Windows 10** дальше отдельно не проверяется: если на Windows 11 всё работает, считаем, что на Windows 10 будет так же, а то, что вылезет, исправляем по факту. Поэтому в столбце Windows 10 вместо открытых вопросов — «не проверяем».
