# Настройки IPv4 — до подключения к сети, прокси — после

Настройки IPv4 в Windows принадлежат адаптеру, а не сети: при переходе из одной сети в другую адаптер приносит с собой прежние. Поэтому переключение идёт в таком порядке:

1. Отключить Wi-Fi-адаптер от текущей сети.
2. Выставить настройки IPv4 профиля новой сети на отключённом адаптере.
3. Подключиться к новой сети и дождаться подключения.
4. Записать настройки прокси.
5. Проверить результат: адрес, доступность шлюза, доступность порта прокси.

Неудачей переключения считается только одно: подключиться не удалось за отведённое время. Тогда настройки IPv4 откатываются к прежним, и инструмент пытается снова подключиться к прежней сети, если она была. Адрес не получен по DHCP (169.254.x.x) или проверка на шаге 5 не прошла — это предупреждение в окне, уведомлении и журнале применений, а не откат: связь с новой сетью есть, и человеку виднее, что делать дальше.

Отката по команде нет: после удачного переключения прежние настройки принадлежат прежней сети, и вернуть их на новой значит получить нерабочее состояние. Вместо этого есть команда «Применить профиль…» для текущей сети.

В обратном порядке получаются две беды. Подключение к сети без DHCP со старыми настройками даёт адрес 169.254.x.x и паузу, пока Windows ждёт DHCP. Подключение к DHCP-сети со статическим адресом от прошлой сети — конфликт адресов или отсутствие связи.

## Consequences

- Когда к сети подключилась сама Windows, наблюдатель применяет профиль уже после подключения: несколько секунд настройки IPv4 будут неверными. Это допустимо. Чтобы Windows реже перескакивала между сетями сама, у сети есть флажок «Не подключаться автоматически». Это не часть привязки: инструмент его не хранит, а читает и записывает режим автоподключения прямо в профиле сети Windows — так флажок доступен и для сетей без привязки и не расходится с галочкой в системном меню.
- Отключение от текущей сети входит в переключение и на время рвёт соединение — это ожидаемо.
- Порядок проверен на Windows 11 26H2 ([проверка записи](../write-check.md), 2026-10-26) и остаётся, но с поправкой. Если статический адрес записан на отключённом адаптере, а шлюз в нём совпадает со шлюзом прежней аренды DHCP (та же сеть, профиль сменился с «Автоматически» на статический), то при первом подключении маршрут по умолчанию пропадает: адрес действует, шлюз отвечает, интернета нет. Похоже, Windows, выключая DHCP, разбирает прежнюю аренду и удаляет маршрут с тем же шлюзом вместе со статическим. Так было во всех четырёх прогонах; с другим шлюзом (переход в другую сеть) маршрут сохранился — это пока один прогон. Следующие подключения с теми же настройками проходят нормально.
- Без маршрута Windows считает подключение ограниченным: через ~16 с перезапускает защиту соединения, ещё через ~16 с — драйвер Wi-Fi (System 4003 «limited connectivity, attempting automatic recovery»), и адаптер отключается от сети. Поэтому проверка на шаге 5 — не только проверка, но и исправление, и первой идёт сразу после подключения: если маршрута по умолчанию через Wi-Fi-адаптер нет за ~3 с, добавить его в действующие настройки (`netsh interface ipv4 add route 0.0.0.0/0 … store=active`; в постоянных он уже записан). Так интернет появляется сразу, и Windows соединение не рвёт (проверено 45 с).
- Запасной порядок для статики — подключиться с прежними настройками и записать статику уже на подключённом адаптере — тоже работает, но несколько секунд в новой сети действуют старые настройки. Пока исправление маршрута работает, к нему не переходим.
- Перезапуск драйвера при «ограниченном подключении» бывает и без нашей записи: на точке доступа телефона он случался через ~32 с после подключения и при DHCP. Неудачей переключения такой разрыв по определению выше не является — подключение уже состоялось.
